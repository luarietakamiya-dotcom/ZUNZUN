# 既知歌詞の同期 設計（A-003 への Claude の返答）

作成: Claude（設計・指示）/ 2026-10-05 / 総指揮: 姫 / 実装・実験: Codex
入力: `docs/CODEX_SYNC_EXPERIMENT.md`（RAB!T・Black Rose の実験）、`docs/AUTO_LYRIC_SYNC.md`、A-001 のレビュー。
**これは設計と実験計画で、精度の主張ではない。** 実曲の検証は Codex の 2 曲だけで、基準時刻（手で合わせた行頭）は無い。下の数値の閾値は、採用判断のための**事前に決める基準案**で、実績ではない。

## 0. 実験結果から言えること・言えないこと
- 言える: (a) tiny は歌唱で大量の歌詞外反復を出し、同期元にならない。(b) small / small_timestamped は日本語の一致が増えるが、複数行をまとめ、取り違えと反復が残る。(c) 反復しない行でも、置換・漢字かな表記違い・脱落・混在言語で崩れる（Black Rose の一意な 34 行のうち、本文がそのまま現れたのは 9 行）。つまり**問題は反復サビの対応だけではない。認識した本文そのもの**が弱い。
- 言えない: 「同期が何割合う」。確定行は 0、±100 ms は未測定。
- 結論（設計の前提）: **ASR の本文を正解として採用しない。既知の歌詞が正解で、音声は「どこで歌われているか」を教える証拠**にする。ASR は「大まかな位置の手がかり」までに格下げし、**最終的な行頭は、既知本文と音響の照合、またはそれによる確認**で決める。

## 1. 全体の方式（段階）
| 段 | 内容 | 出力 | 自動適用 |
|---|---|---|---|
| S0 | 既知歌詞の前処理（第 2 章） | 行ごとの正規化表記・読み・手がかり | — |
| S1 | 粗い位置づけ: ASR の語時刻 + 歌声帯域の onset（既存のタップ吸着の仕組み）から、**行の順序を保つ最適な割り当て**（第 3 章） | 各行の候補区間・信頼度・曖昧さ | しない |
| S2 | 精密化（実験 E2・E3）: **既知本文を固定して**音声と照合（強制デコード + 注意の DTW、または CTC 強制アラインメント） | 行・語の時刻 | しない |
| S3 | 検証: 歌声の onset と ±150 ms の範囲で整合するか、単調か、長さが妥当か | status（確定候補・要確認・未確定） | しない |

## 2. 読みの正規化（A-003 (1)）
### 2.1 原則
- 正規化は**比較のための別表現**で、元の歌詞テキストは変えない（保存・表示は元のまま）。
- 日本語・英語・数字・記号・混在（RAB!T のような装飾表記）を**連続する文字種ごとに分けて**処理する。

### 2.2 段階 1: 依存なし（まずこれで測る）
順に適用して比較用文字列を作る。
1. NFKC。全角英数→半角、半角カナ→全角カナ。
2. 括弧書き・ルビ記法（`漢字《かな》` / `(…)`）は、**かな側を読みとして保持**して本文から外す（歌詞パネルの任意の読み指定。無ければ何もしない）。
3. カタカナ→ひらがな。長音符「ー」は直前の母音に置き換え（例: ラビット→らびっと、コー→こお）。小書き文字（ゃゅょっ）はそのまま保持。
4. 記号・空白・句読点・歌詞の `/` を除去。英字は小文字。
5. 数字は、日本語の文脈では読みに展開しない（段階 1 では除去せず、そのまま比較して不一致を許容）。
6. **別名表（エイリアス）**: 装飾表記（`RAB!T`・`Black Rose` など）を、利用者が `rab!t=らびっと,rabbit` のように登録できる（Project JSON の任意項目。`sanitizeProject()` を通す）。段階 1 ではこれが混在言語への唯一の手当て。
- **漢字は読みに直せない**ので、漢字は**表記のまま**比較する。ASR が漢字で出す箇所は一致する。ASR がかなで出す箇所は、漢字との不一致として扱う（失点を軽くする: 漢字 1 字をかな 1〜3 字と等価に見る許容幅を持つ）。

### 2.3 段階 2: 読み辞書（依存追加・姫の了承後）
- 形態素解析（例: kuromoji 系。辞書は数十 MB 規模の可能性。ライセンス・容量・読み込み時間を実測してから）で、**漢字かな交じりの歌詞をかなの読みに変換**する。歌詞の読みは「歌唱の読み」と違う場合（当て字・ルビ）があるので、利用者の読み指定（2.2 の 2）を優先する。
- 英語の部分は、カタカナの読み（らびっと）とローマ字（rabbit）の両方を**複数の読み候補**として持ち、どれかに一致すれば良い。英語の発音辞書（巨大）は入れない。
- 依存を入れる前に、段階 1 のままで目標に届くかを実験で確認する（無駄な依存を増やさない）。

### 2.4 比較（類似度）
- 行 L の正規化文字列と、ASR の連続した語の並び U（時刻つき）の**部分一致の最適なずれ**（局所アラインメント）で、`score = 1 − 編集距離 / max(長さ)` を出す。部分一致を許す理由は、ASR が複数行を 1 区間にまとめるため。
- 置換の重みは、同じ音の候補（か↔が、は↔わ、へ↔え、お↔を）を軽く、漢字↔かなの置換も軽く、それ以外を重くする（例: 軽 0.4・重 1.0。値は初期案）。
- 閾値の初期案: `score ≥ 0.8` 強、`0.5〜0.8` 中、`< 0.5` なし。**これらは実験で決め直す**。

## 3. 反復サビを含む行の対応付け（A-003 (2)）
**出現順と文脈**を使い、行の列と ASR の単位の列を**順序を保つ全体最適**で対応付ける（動的計画法）。

- 状態: 行 i を、時間順の ASR 単位列の連続した区間 [a, b] に割り当てる、または「未割り当て」にする。
- 費用: (1) 読みの不一致（第 2.4 の `1 − score`）、(2) **未割り当て・飛ばした単位の罰**、(3) **順序の制約**（行 i+1 の区間は行 i の区間より後）、(4) **長さの事前分布**（その行の拍数・文字数から期待される長さの 0.5〜3 倍に収まる。曲全体の歌の速さは、確度の高い行から推定して更新）、(5) **区間見出し（`[サビ]` など。既に `section-cues.ts` が解釈）の事前分布**: 同じ見出しの 2 回目は、1 回目より後、間の部分を挟む。
- **同じ文面の行が複数あっても、順序制約で別の箇所に割り当てられる。**「走れ Rabbit」のように ASR の同じ箇所が複数行に一致する場合は、**行の出現順と前後の行（文脈）**で解く。曖昧さが残る場合は、割り当てを複数（上位 K = 3）持つ。
- **曖昧さの指標**: 行ごとに、最適解と、その行だけ別の割り当てにした次善解の費用差（マージン）。マージンが小さい行は**要確認**にし、確定候補にしない。
- 反復する本文の行は、1 回目の確定がずれていると 2 回目以降が連鎖でずれる。**連鎖の誤りを防ぐ**ため、人が確定した行を**固定点**にして、残りを再計算できるようにする（第 4 章）。
- 出力: 行ごとの `{ start, end, score, margin, alternatives[], flags[] }`。

## 4. サブワードを行へ集約し、未確定を見せる UI（A-003 (3)）
### 4.1 集約（サブワード → 行）
- ASR の語時刻には、**ゼロ幅のサブワード断片**がある。**直前（なければ直後）の単位へ併合**してから行へ集約する。モデル破損の件数としては数えない（Codex の指摘のとおり）。
- 行の開始 = その行に割り当てた最初の単位の開始、終了 = 最後の単位の終了。
- **1 つの ASR 単位が複数行にまたがる場合**: 単位の中を文字数で按分して**推定**し、`flags: ['estimated-split']` を付ける。推定は確定候補にしない。
- 一致が部分的（一致した文字が 60 % 未満）、時刻が逆転・ゼロ長・範囲外、前後の行と逆順、は `flags` に理由を持つ。
- **検証は 2 種類に分ける**: (a) 出力の構造（有限・範囲内・単調。Codex の `validation.js`）、(b) 行境界としての妥当性（長さ・順序・音響との整合）。

### 4.2 status（3 段階）
| status | 条件（初期案） | 表示 |
|---|---|---|
| 確定候補 | `score ≥ 0.8` かつ マージン十分 かつ 歌声の onset と ±150 ms で整合 かつ `estimated-split` なし | 緑。**まだ未適用。**人が試聴して採用 |
| 要確認 | 上のどれかを満たさない | 黄。候補時刻と、理由（フラグ）を表示 |
| 未確定 | 候補なし | 灰。時刻は出さない（仮の均等割りも出さない） |

### 4.3 確認 UI
- 行ごとに: 歌詞、候補時刻、status と理由、**▶ 試聴（候補の 1 秒前から再生）**、採用／±10 ms 刻みで微調整／「ここに合わせる」（再生位置を行頭にする。既存のタップと同じ）、ロック。
- 上部に集計: 確定候補 n 行・要確認 n 行・未確定 n 行。「**認識で同期できた行数**」という言い方はしない（本文が現れた行数を、正しく同期した行数として数えない）。
- **採用した行は固定点**になり、残りの行を再計算する（第 3 章）。手で合わせたタップ時刻（既存）は上書きしない（ロック優先）。
- 音声の歌声帯域の強さと候補の位置を、波形の上に重ねて見せる（確認しやすくする）。
- 自動適用ボタンは作らない。「確定候補をすべて採用」は、**確定候補だけ**を対象にし、件数と取り消しを出す。

## 5. 基準時刻と評価手順（A-003 (4)）
### 5.1 基準時刻
- **基準 = 姫が手で合わせた行頭時刻**（既存のタップ。音を聞いて合わせたもの）。1 曲 50〜120 行を、姫が全部合わせるのは重いので、**サンプル 20〜30 行/曲**（曲全体から等間隔 + 反復サビ・混在言語の行を含める）で足りる。
- 基準自身の誤差（人の反応のばらつき、約 ±50〜100 ms）を、**評価の下限**として報告に書く。±100 ms の達成率は、基準の誤差より厳しくは測れない。

### 5.2 曲の選び方
最低 4 曲: (a) 反復サビのある曲（RAB!T）、(b) 反復のない曲（Black Rose）、(c) ゆっくりした曲、(d) ラップ混じり／速い曲。**調整用と評価用に分ける**（閾値を決めた曲で評価しない）。調整に 2 曲、評価に 2 曲以上。

### 5.3 指標
行頭の誤差（候補 − 基準）の分布: **中央値・±100 ms・±300 ms・±1 s の割合**、**候補を出した行の割合（カバー率）**、**確定候補と判定した行の精度**（±300 ms 以内の割合）。曲ごとに出し、平均だけにしない。標本が小さいので、割合は**区間（Wilson）**付きで書く。

### 5.4 比較する方式（切り分け）
1. ASR 本文のみ（現状）。2. ASR + 全体最適（第 3 章）。3. 2 + 歌声 onset の吸着。4. **既知本文を固定した照合（E2・E3）**。5. 比較対象として、**手で合わせた少数のアンカー間の均等割り**（これより悪いなら価値がない）と、既存のタップ吸着。**どこまで効くのかを段階ごとに示す**。

### 5.5 採用の事前基準（姫の判断 2026-10-05 反映）
**姫の回答**: 基準時刻は既存の `lineTimes` でよい。採用基準は「できれば 90」。Claude は「確定候補の ±100 ms 以内の割合を 90 % にしたい」と解釈した（違えば知らせてほしい）。**90 % は目標で、達成の保証ではない。** 手で合わせた基準自身の誤差が ±50〜100 ms あるため、90 % を測れる限界に近く、達成を確かめられない場合がある。その場合は「測れなかった」と書く。
- **目標**: 評価用の曲すべてで、**確定候補の 90 % 以上が ±100 ms 以内**（かつ ±300 ms 以内は 98 % 以上）、確定候補が全行の 30 % 以上。**採用の最低ライン（案のまま）**: ±300 ms 以内が 90 % 以上、±100 ms 以内が 70 % 以上。最低ラインを満たせば「確定候補の表示 + 人の確認」として出し、目標の 90 % に届くまでは「高精度」とは表示しない。最低ラインも満たさなければ「**候補表示 + 人の確認（B2 の弱い形）**」に留め、自動適用は永久にしない。
- 基準を満たさない曲の種類（ラップ・混在言語など）を、利用者に**事前に伝える**（品質表示）。

## 6. 次の実験（Codex。コードは製品に入れない。リポジトリ外）
優先順。**各実験で、同じ曲・同じ基準で第 5 章の指標を出す。**
- **E0（最優先・安い）: 声の stem で同じ実験をやり直す。** ミックス音源は、伴奏が ASR を崩す最大の原因の可能性が高い。**ボーカルだけの音声は、MusicSync からは出せない**（B0 の読解どおり、自動のボーカル分離も声だけの書き出しも無い）。**姫が用意するボーカルだけのファイル**（ZUNZUN の「ボーカル stem（吸着用）」欄に読み込むものと同じ入手元）を、同じ 2 曲に適用し、ミックスと比較する。**元曲との位置のずれ（offset）は姫に確認**し、分からなければ歌い出しなどから測る。既定値 0 を一致の証明にしない。（訂正 2026-10-05: 当初「MusicSync の stem」と書いたのは Claude の読み違い。MusicSync 連携の価値の裏づけにはならない。）
- **E1: 第 2・3 章（段階 1 の正規化 + 全体最適）**を、既存の ASR 出力に適用。モデルを再実行せず、保存済みの語時刻で測る。基準時刻が無いうちは、**被覆と曖昧さ（マージン）の分布**だけ出す。
- **E2: 既知本文を固定した強制デコード**。Whisper に、既知歌詞の行を**デコーダの入力として固定**し、注意（cross-attention）の DTW で語時刻を取る（stable-ts の align と同じ考え方。**依存として入れず、方式の再実装**）。窓（30 秒）ごとに、S1 の粗い位置から行を割り当てて実行。**本文を固定するので、置換・表記ゆれ・混在言語の問題が消える**（本文を認識しないため）。ハルシネーションも防げる。見るのは時刻の精度と、窓の境界。
- **E3: プロンプトによる誘導**: ASR の初期プロンプトに、その窓の歌詞を与えて、認識本文の置換・脱落が減るかを見る（`prompt_ids` が使えるか確認）。
- **E4（任意・重い）: CTC 強制アラインメント**（多言語の音素モデル）。容量が大きい（数百 MB 規模の可能性）。E2 が不十分なときだけ。比較用。
- **幻覚の検知（共通）**: 圧縮率（反復の検知）、`no_speech` の確率、平均対数確率、歌詞外の語の割合で、棄却する（無音の棄却と同様）。

## 10. E0 の結果を受けた改訂（2026-10-05）
E0（ミックス vs 声だけ）の結果: 位置のずれは両曲とも 0 秒（5 窓すべて、波形相関で測定）。**本文一致（一意な行・両端候補）は RAB!T 38→39/67、Black Rose 9→11/34。声だけにしても、本文の認識はほとんど良くならない**（新規 5・消失 4 など、増減が相殺）。基準時刻（`lineTimes`）が無く、行頭誤差は測れていない。

### 10.1 読み取ったこと
1. **伴奏の除去は、本文の認識の主因ではない。** 声だけでも、完全一致（NFKC・大小文字・記号除去のみ）で RAB!T は 58 %、Black Rose は 32 %。**ASR（Whisper small 系）が歌唱の本文を安定して書き起こせないのが根本。** よって「ASR の本文を、既知の歌詞に合わせる」方式（第 2・3 章）だけでは上限が低い可能性が高い。
2. **ただし「完全一致」は厳しい指標**で、置換・脱落を許さない。E1（読みの正規化 + 部分一致 + 順序の全体最適）を適用すると、被覆はかなり増える可能性がある。**E0 の数字は E1 の下限であって、方式の限界ではない。**
3. **声だけの音声は、本文より「いつ歌っているか」に強い。** 声だけなら、無音（息継ぎ・間）と発声の立ち上がりを**音の強さだけで**取れる。これは ASR の本文に依存しない。→ **第 3 章の S1 に、声だけの音声があるときの経路を足す（10.2）。**
4. 本文を認識させず、**既知の歌詞を固定して**音声と照合する E2 の期待が、相対的に高まった（本文の認識の弱さを、そもそも使わない）。

### 10.2 S1 の追加経路: 発声区間（フレーズ）に基づく割り当て（声だけの音声があるとき）
- **フレーズ検出**: 声だけの音声の短時間エネルギー（例: 20 ms 窓）に、ヒステリシス付きのしきい値を当て、**発声区間**（開始・終了）を取る。最小の無音 150 ms 程度（初期案）で区切る。**行頭の候補を、ASR ではなく音の立ち上がりから**取る（精度の期待は ±50 ms 程度。**未検証**）。
- **割り当て**: 歌詞の行の列と、フレーズの列を、第 3 章と同じ**順序を保つ動的計画法**で対応付ける。費用は、(1) 行の文字数（拍数）から期待される長さと、フレーズの長さの差、(2) 区間見出し（`[サビ]` など）、(3) **ASR の本文の部分一致**（あれば加点。無くても動く）、(4) 飛ばし・併合の罰（1 行が複数フレーズ、複数行が 1 フレーズを許す）。
- 弱点（正直に）: 息継ぎのない長いフレーズ、ささやきや語りの行（Black Rose の冒頭 5 行）、コーラスの重なり、ラップの連続した発声は、フレーズに分かれない。その行は**要確認**にする。1 フレーズに複数行が入る場合は、文字数で按分した**推定**（確定候補にしない）。
- 声だけの音声がない（ミックスだけ）ときは、この経路は使えず、品質が下がることを利用者に表示する（品質表示）。**ZUNZUN には既に「ボーカル stem（吸着用）」欄があるので、自動同期は stem があるときの機能として設計する**（ミックスだけのときは、手の同期 + 既存の吸着が基本）。

### 10.3 基準時刻が無いことへの対処（最優先の課題）
基準が無いと、どの方式の精度も言えない。Codex は既存の `lineTimes` を見つけられなかった。次の順で解決する。
1. **姫が、2 曲の `*.zunzun.json`（タップ済み）を持っていれば Codex へ渡す。** 行頭が全行そろっていなくてもよい（手で合わせた行だけ使う）。
2. 無ければ、**ラベル付けページ**を Codex が作る（リポジトリ外、使い捨て）: 行ごとに、候補時刻の 1 秒前から試聴 → 「合っている」「ずれている（+/− ms を入れる、または再生位置を行頭にする）」「分からない」を選ぶだけ。**姫の作業は 1 曲 20〜30 行（等間隔 + 反復・語り・混在言語の行）**。基準の誤差（人の反応）は ±50〜100 ms と報告に書く。
3. どちらも難しければ、基準なしで被覆とマージンの分布だけを見て、**「採用の事前基準」は評価できない**と明記する（達成を主張しない）。
